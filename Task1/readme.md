## Анализ текущих проблем

1. **Сайт медленно грузится** — из-за монолита core-app и недостаточного масштабирования.
2. **Нарушается SLA для B2B** — нет rate limiting и защиты от скачков нагрузки от партнёров.
3. **Приложение падает, реагируют медленно** — нет мониторинга, алертинга, и система развёрнута в одной зоне.

## Проектирование целевой архитектуры (to-be)
### 1. Стратегия масштабирования и отказоустойчивости

**Горизонтальное масштабирование** будет эффективнее, так как:
- Позволяет справляться с ростом нагрузки добавлением новых инстансов
- Повышает отказоустойчивость
- Позволяет изолировать нагрузку от партнёров и пользователей

**Использование нескольких зон доступности (AZ)** обязательно, так как:
- Требуется 99,9% доступности
- RTO 45 мин., RPO 15 мин. не могут быть достигнуты в одной зоне
- Пользователи по всей РФ должны получать одинаковую производительность

### 2. Конфигурация развёртывания в Kubernetes

**Использовать один глобальный Kubernetes кластер, развёрнутый в нескольких зонах доступности**, потому что:
- Упрощает управление инфраструктурой
- Позволяет автоматически распределять поды между зонами
- Упрощает реализацию межзональной балансировки нагрузки
- Поддерживается Yandex Cloud (Managed Kubernetes в нескольких AZ)

### 3. Балансировка нагрузки

**Многоуровневая балансировка**:
1. **Глобальный балансировщик (Yandex Application Load Balancer)** с геораспределением
2. **Ingress-контроллеры** в каждом кластере Kubernetes
3. **Service Mesh** (Istio или аналоги) для управления трафиком между сервисами

**Health checks** будут настроены на всех уровнях:
- На уровне L7-балансировщика
- На уровне Ingress
- На уровне Kubernetes readiness/liveness probes

### 4. Фейловер-стратегия

**Active-Active архитектура** с геораспределением:
- Трафик распределяется между зонами по принципу "ближайший к пользователю"
- Автоматический фейловер при проблемах в одной зоне
- Session persistence для сохранения сессий пользователей

### 5. Конфигурация базы данных

**PostgreSQL с синхронной репликацией**:
- Мастер в AZ1, синхронная реплика в AZ2
- Асинхронные реплики для чтения в других AZ
- Использование Patroni для автоматического фейловера
- RPO 15 мин. обеспечивается синхронной репликацией
- RTO 45 мин. обеспечивается автоматическим фейловером

**Резервное копирование**:
- Ежедневные полные бэкапы
- Непрерывное архивирование WAL
- Хранение бэкапов в Yandex Object Storage

### 6. Шардирование БД

**Пока не требуется**, так как:
- Общий объём данных всего 50 GB
- PostgreSQL справится с таким объёмом на одном инстансе
- Шардирование добавит сложности без необходимости
- При росте объёма данных можно будет перейти на шардирование позже

## Дополнительные улучшения

1. **Выделение B2B и B2C трафика**:
    - Отдельные ingress-контроллеры
    - Rate limiting для партнёров (до 20 RPS)
    - Приоритизация трафика

2. **Кэширование**:
    - Redis кластер для кэширования продуктов и статики
    - CDN для статических ресурсов

3. **Мониторинг и алертинг**:
    - Prometheus + Grafana
    - Мониторинг всех компонентов
    - Автоматические алерты при проблемах

4. **Оптимизация монолита**:
    - Выделение критических сервисов из core-app
    - Внедрение асинхронной обработки
